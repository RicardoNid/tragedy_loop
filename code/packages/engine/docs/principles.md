# 设计原则

状态：重写的初始工程约束。这里定义设计方向；已实现范围见 milestones.md。

1. **规则与机制分离。** 执行器识别通用操作，不识别具体角色、身份或模组名称。使用既有操作的新内容只增加规则数据及验收样例；新机制需要先明确语义，再扩充操作集合。
2. **确定性。** 固定规则定义、初始状态、操作者及完整命令序列，得到相同的状态和轨迹。玩家选择是显式输入，执行器不代选；随机策略位于执行器之外。
3. **严格失败。** 未实现操作、未知字段和无效引用在编译时拒绝。规则缺陷与非法玩家输入分开报告，均不修改输入状态。缺失语义不作为无效果成功处理。
4. **受限表达。** 规则使用可校验的数据结构；禁止嵌入任意代码、I/O、时间读取和隐式随机。逐步增加表达能力，不预先构造通用编程语言。
5. **显式结算。** 同时性、选择权、替代与禁止、使用次数消耗时点及失败检查边界都需要明确契约。数组顺序不能代替未决的纸质规则。
6. **信息隔离。** 完整状态仅供可信执行环境。未来的玩家视图必须按白名单构造，并审计动作列表、错误和轨迹；当前 package 尚未提供安全玩家投影。
7. **可解释与可重放。** 每步绑定具体规则和命令，保留可校验的状态记录。自然语言日志不是执行依据。
8. **证据边界。** 随机运行没有发现反例，不等于规则正确或穷尽验证。真实内容须有来源、人工校对及独立预期样例；旧引擎输出不是正确性的唯一依据。

源码保持单一 JS 执行核心，CLI 是 Node 适配器；Python 服务及未来 Web 通过适配使用同一语义，不维护第二套规则解释器。未引入构建器或第三方依赖，后续是否采用 TypeScript 另作决定。
